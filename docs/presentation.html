01

Private requests.
Provable balances.

Anonfolio is a static Ethereum portfolio reader. It sends requests through Anon-RPC and Tor, then verifies balances inside the browser.

Ethereum mainnetETH · WETH · custom ERC-20sNo wallet connection or signing
An RPC operator supplies the evidence. Your browser decides whether the result is valid.

Speaker notes

The project separates transport privacy from execution correctness. Anonymizing a request does not make the RPC response correct; a proof does not hide the address being queried. Anonfolio addresses both with separate components. This is a read-only application: it does not hold private keys, sign messages or send transactions.

Code: main.ts orchestrates the UI and explicit address refreshes. Implementation reference: commit 012caa8; dependency versions describe this repository snapshot.

02

A portfolio, without connecting a wallet.

  • Track named addresses and custom tokens with browser-local icons.
  • Refresh one address; inspect timestamped verification logs and errors.
  • See token totals and optional direct-pool price estimates.
  • Reopen saved data offline. New reads start only when requested, except retries for an active failed read and initial reads for newly added addresses.

Speaker notes

The UI shows at most two decimal places, but stores raw bigint values. Proven zero holdings are omitted from compact address rows. Unknown or failed values are not silently converted to zero. Adding a token or explicitly saving pricing settings refreshes tracked addresses; merely reopening the application does not.

The screenshot is embedded in this file, as are the technology logos. Opening the presentation does not load the application, start its workers, contact providers, or read a saved portfolio.

03

Privacy, authenticity and availability
are separate concerns.

Privacy

Tor routes requests away from the browser’s public IP. Each address gets its own isolation key.

Anon-RPC + tor-js

Authenticity

Consensus establishes a trusted state root. Proofs and local EVM execution bind the answer to it.

Helios + Merkle proofs

Availability

Gateways, Tor routes and providers can fail. Timeouts, retries and saved values keep the UI usable.

Fail closed + local cache

The RPC still sees the requested address. Different isolation keys do not guarantee different Tor exit IPs.

Speaker notes

The browser trusts the deployed application, its reviewed binaries and a recent independently selected mainnet checkpoint. An RPC response is untrusted until verified. A gateway can observe the connecting browser IP; Tor is not a guarantee against traffic correlation or colluding observers. A correctly pinned binary can still contain a vulnerability: integrity is not a substitute for review.

Direct HTTPS is a separate, explicitly selected mode. It keeps verification but exposes the browser IP to providers; Tor failure never selects it automatically.

Speaker notes

Helios and revm run as vendored Rust/WebAssembly behind generated JavaScript glue. viem does not provide an ordinary-fetch fallback for balance reads; its role here is ABI/address and numeric utilities. EthereumJS Trie is an additional browser-side proof check in front of Helios’s own verifier.

The platform also uses Web Crypto, Web Workers, localStorage, Web Locks and a service worker. Playwright tests browser behavior. IPFS/Kubo and Docker support optional publishing; neither is an application backend. Versions are pinned in package.json and the vendor review files.

Speaker notes

Anon-RPC 0.4.0 defines a transport-neutral capability API. The browser harness creates an opaque-origin iframe and puts the anon-client worker inside it. Host-side bridges handle transport and storage. Anonfolio separately starts its Helios worker; that worker’s execution fetch is adapted to send RPC messages through the main-thread bridge.

The Tor worker maintains its own Tor state through harness storage. The app’s portfolio uses localStorage instead. These are separate storage purposes and trust boundaries.

06

Pin code first. Start the private route.

  1. Resolve the bundled Tor worker locally

    A narrow specifier provider answers worker hash and URL lookups from release metadata.

  2. Verify before executing

    The harness checks Keccak-256 of the worker bytes, then starts the sandbox.

  3. Connect through configured gateways

    An optional public directory mirror can seed Tor; Tor authenticates directory data.

  4. Initialize Helios on a requested read

    Download local WASM, check SHA-256, then bootstrap consensus from the selected checkpoint.

Release trust inputs

Tor worker digest   → Keccak-256
Helios WASM digest  → SHA-256
Mainnet checkpoint  → root + slot
Gateway identity    → certificate hash
Page open starts transport startup. It does not automatically refresh saved balances.

Recovery exception: “Update Tor worker from PublicNode” explicitly performs direct metadata/download requests and changes the selected worker trust pin. No tracked addresses are included.

Speaker notes

The harness normally supports on-chain discovery. Anonfolio avoids that bootstrap RPC by supplying a reviewed local specifier provider in bootstrap.ts. The raw Tor worker bytes are emitted without transformation. The optional directory mirror is fetched directly, but carries public directory data rather than watched-address queries.

A user-applied worker update trusts PublicNode’s chosen digest and code; it is not covered by the bundled release review. A custom checkpoint is also a deliberate trust decision. The app checks syntax, age and matching bootstrap slot, but the user must compare the root against independent trusted sources.

07

Messages carry requests. Proofs carry trust.

  1. Helios → main thread

    rpc {run, id, body}

  2. Main thread → Anon-RPC

    fetch with the wallet’s isolation key.

  3. Tor → execution RPC

    HTTPS JSON-RPC through the private route.

  4. RPC → Tor

    Return proof, bytecode or block data.

  5. Anon-RPC → main thread

    Return the response stream.

  6. Main thread → Helios

    reply {id, data}; verify before accepting a result.

run identifies the wallet session; id correlates an individual pending request.

Helios then emits balance, price, progress or failure events. The UI saves accepted results.

Speaker notes

In helios.worker.ts, the fetch adapter posts {type:'rpc', run, id, body}. The main thread chooses the wallet’s current RPC route, calls worker.fetch, bounds and parses the response, then posts a reply with the correlation ID. The worker’s pending-promise map resumes the original WASM call. The bridge correlation ID is separate from the JSON-RPC body’s own ID, which is also validated. Run checks and worker identity checks discard stale replies after cancellation.

This sequence expands one execution request. The harness internally uses iframe/worker capability messages; the public fetch call abstracts those hops. Consensus GET requests use a different message type and a separate shared isolation key, including during background consensus synchronization. Source: client.ts and helios.worker.ts.

Identity and isolation

KPS pins a peer certificate hash. Tor builds circuits over the provided transport. A random per-address anonOptions.isolationKey stays with balance/proof/oracle retries.

Separate service destinations

Execution requests go to configured mainnet RPC operators. Beacon light-client requests go to the pinned consensus API on a separate shared route.

The gateway is transport infrastructure, not the execution RPC. No balance request falls back to ordinary browser fetch in Tor mode.

Speaker notes

Key-Pinned Streams supplies secure multiplexed streams addressed by a pinned certificate identity; the browser implementation uses WebRTC/DTLS. Anon-RPC grants this transport as a host capability. tor-js uses it to reach Tor infrastructure. KPS alone is not an anonymity network.

The bundled development configuration has one demo gateway. Gateway availability and browser UDP/WebRTC reachability are practical constraints. The app may try another configured execution RPC after an explicit historical-proof rejection, but retains the isolation key and exact requested block. Ordinary transport or verification failures fail closed. Different address keys are not a promise of distinct exits or operators.

Speaker notes

One EthereumClient lives in the shared Helios worker. It bootstraps from the selected checkpoint and authenticates consensus updates; execution metadata is checked against the block hash authenticated by consensus. The app then applies timestamp bounds to the selected finalized execution block. It rejects checkpoints outside a 14-day trust window and selected blocks more than one hour old or more than one minute in the future.

The WASM artifact is SHA-256 pinned and comes from reviewed Helios 0.12.0. The review includes PR #813 binding account proofs to the requested address. Source and trust inputs: trust.ts, vendor review.

  1. Bind the response to the requested wallet

    A valid proof for another address is rejected.

  2. Check the path against the authenticated root

    Wrong-block or modified account data cannot pass.

  3. Accept the raw bigint balance

    A zero value needs a valid inclusion or non-inclusion proof. A failed request is unavailable, never zero.

Speaker notes

EIP-1186 describes account and storage witnesses returned by eth_getProof. The adapter verifies the requested address, account path and account RLP fields against the finalized state root, and requires every requested storage slot to appear. Helios independently validates its inputs as well.

The app calls Helios’s local get_balance API; its adapted execution transport issues eth_getProof. It does not use an unverified remote eth_getBalance result. The JSON snippet illustrates the pinned block-hash selector used by the adapter. Source: proofs.ts.

Proxy-aware execution

Implementation contracts, delegated calls and additional storage are discovered during execution and verified through the same private route.

Display metadata stays explicit

The user supplies token symbols, decimals and icons. The app does not call decimals(). WETH is an ordinary ERC-20 included by default.

The execution bridge permits proof, code and block requests. Remote eth_call is not an authoritative execution shortcut.

Speaker notes

The worker invokes EthereumClient.call on the pinned block. The reviewed Helios/revm integration fetches verified account, bytecode and storage dependencies as required. Before code is used, the adapter additionally checks Keccak-256 against the proven code hash. Missing requested slots and malformed return data are rejected. User-configured decimals affect display, not the proven raw integer.

The RPC method allowlist is eth_getProof, eth_getCode, eth_getBlockByHash and eth_getBlockByNumber. Remote access lists are not trusted: the adapter rejects eth_createAccessList and demand-loads verified state instead. The separate manual worker updater may issue metadata eth_call requests; that is not the balance execution path.

A 30-minute TWAP from one direct pool.

Uniswap v3 → USDC by default

Finalized time − 1,800sFinalized block time
observe([1800, 0]) · schematic window, not market data
meanTick = floor(ΔtickCumulative / 1800)
rawRatio ≈ 1.0001 ^ meanTick
holdingValue = rawBalance × orientedRatio
  1. Validate the direct pair

    Resolve through the canonical v3 factory; check pool factory, tokens and fee.

  2. Require history and liquidity

    30-minute observations plus sufficient current and harmonic virtual quote reserves.

  3. Use the balance’s verified block

    Oracle calls run locally over proven state. No multihop routes or external price API.

ETH and WETH exclusively use the WETH/USDC 0.05% pool with USDC selected. Missing direct pool → unpriced holding → partial portfolio total.

Speaker notes

The oracle executes the same verified local-call path as token balances. For other pairs it checks fee tiers 100, 500, 3000 and 10000, and chooses one qualifying pool by harmonic quote-side depth with a deterministic address tie-breaker. Quote-token holdings need no conversion pool. A WETH-only route never qualifies for a USDC quote.

The TWAP uses the geometric mean tick, including correct negative rounding and accumulator wrapping. tickRatio uses bigint fixed-point exponentiation with 512 fractional bits; holding values remain rational bigint fractions until display. Virtual liquidity checks are filters, not executable trade quotes or TVL measurements. References: Uniswap v3 price oracles, pool contract, pricing.ts.

14

Preserve the last result. Explain the next attempt.

Proven zero

A valid proof returned zero. This is a successful result, not an empty UI placeholder.

Unavailable

No accepted amount exists. Show a reason and retry action; do not substitute zero.

Stale / saved

Keep the previous amount and provenance visible when refreshing fails or data are restored.

Persistence

localStorage stores balances, block identity/time, quotes, settings and errors. Web Locks serialize merges; newer finalized blocks win. Cross-tab updates start no reads.

Bounded recovery

Failed reads and transient price failures retry on the address’s route. Permanent “no qualifying pool” errors stay unpriced. Removal aborts active and queued work.

Speaker notes

The version-3 portfolio is stored under anonfolio.portfolio.v2 for migration compatibility. Atomic balance records retain raw amounts, timestamps, block metadata, configured decimals, estimates and error details. Three-way merges preserve independent edits, let removals win, and reject lower finalized block numbers. Successful-read time breaks ties at the same height. Price failures include their quote-settings identity and retry classification.

Balance and transient pricing backoff is 2, 4, 8, 16, 32 and at most 60 seconds. Connection retry backoff caps at 10 seconds; Tor’s internal guard backoff is separate. RPC attempts and verifier sessions have hard deadlines; decoded execution/consensus bodies are bounded to 16 MiB. Reopening the page starts no saved balance/price reads. Browser storage is not encrypted. Sources: storage.ts, balance-freshness.ts, retries.ts and response-body.ts.

Speaker notes

The simple Bun server serves dist only; it is not an RPC proxy. Optional Docker/Kubo publishing checks the uploaded CID against the build CID and can export a CAR archive. Prefer a subdomain IPFS gateway to keep a distinct browser origin per CID; path gateways can share storage origins. Changing origin/CID does not migrate portfolios automatically.

The app caches the exact application asset list and its pinned binaries. Direct HTTPS omits the unused Tor bundle from eager caching. Browser verification still depends on a working provider when new data are needed. There is no application-owned analytics, remote font service or external pricing API.
